# Persistence — `src/db/`

Postgres hosted on Supabase. **Drizzle is migrations-only**: no application query goes
through it (the app talks to PostgREST via `supabase-js`), so `DATABASE_URL` is needed
only by `db:migrate`. Supabase also carries the back office's auth and the product photo
storage — that is what a move off it would have to replace.

| File                      | Role                                                                 |
| ------------------------- | -------------------------------------------------------------------- |
| `schema.ts`               | Tables, relations, RLS policies, inferred types. Importable anywhere |
| `client.server.ts`        | Drizzle connection. **Server-only**                                  |
| `migrations/`             | Generated by drizzle-kit — never hand-edit (also prettier-ignored)   |
| `../../drizzle.config.ts` | CLI config; loads `.env` itself via `process.loadEnvFile`            |

## Invariants

- **Never touch the database from a route `loader` or a component.** Loaders are
  isomorphic — they run in the browser too. Go through `createServerFn`; the
  `.server.ts` suffix fails the build with the full import chain.
- **`db` and `serverEnv` are functions, not objects.** A module-scope `process.env` read
  can be inlined into a bundle, and edge runtimes inject the env per request, so it
  evaluates to `undefined` on the server too. Validation happens on first use: a missing
  `DATABASE_URL` fails the first request, not process startup.
- **`prepare: false` is required** — the Supabase pooler runs in transaction mode, where
  a prepared statement isn't guaranteed to find its session again.
- **`casing: 'snake_case'` is set in two places** (`drizzle.config.ts` and the runtime
  `drizzle()` call) and must stay in sync, otherwise a column without an explicit name is
  created as `snake_case` but queried as `camelCase`.
- **Prices are integer cents** (`price_cents`), never floats. Currency lives on the venue.
- **`authUid` belongs in policies, never in a `DEFAULT`.** `drizzle-orm/supabase` exports
  it as `(select auth.uid())` — the wrapper makes Postgres cache the value per query
  (InitPlan) inside a policy, but a `DEFAULT` rejects any subquery outright (`0A000`).
  Column defaults must use bare sql`auth.uid()`.

## RLS

Enabled on all five tables, and **the policies live in `schema.ts`** (`pgPolicy` +
`anonRole`/`authenticatedRole` from `drizzle-orm/supabase`), not in hand-written SQL —
the schema stays the source of truth. `drizzle.config.ts` sets
`entities.roles.provider: 'supabase'` so drizzle-kit doesn't create or drop the
Supabase-owned roles.

This is the real tenant boundary. Supabase exposes the `public` schema through PostgREST
and grants rights to `anon`/`authenticated`, so a table without RLS is readable **and
writable** by anyone holding the publishable key, which ships in the browser bundle. A
`beforeLoad` guard protects a screen, not the data.

Policies: public `SELECT` on `venues`, `categories` and `products`, plus an owner-scoped
`INSERT`/`UPDATE`/`DELETE` triple per table for `authenticatedRole`, generated by the
helpers at the top of `schema.ts` (`publicRead`, and the owner triple whose `check` goes
into both `using` and `withCheck`).

**`orders` and `order_items` are the exception, and it is the point.** They carry _no
policy for `anon` at all_ — not even read. The customer who orders is `anon`, and opening
that table to them would publish a free `insert` on the internet (any total, any status,
any venue) and let anyone read the neighbour's order by changing one digit. They reach the
data only through the two `security definer` functions of migration `0009`. `orders` gets
an owner `select` and an owner `update` (the bar advances the status); `order_items` gets
an owner `select` alone — a line is a trace, it is never edited. Neither gets a `delete`:
history that vanishes on a click is not history.

**`venues` carries two permissive SELECT policies**, OR'd: `venues_public_read` requires
`deleted_at is null`, `venues_owner_read` lets an owner see all of theirs. Dropping the
second would make a binned venue invisible to its own manager — unrestorable — and the
category write policies, which look the venue up by subquery, would stop finding it.

**Drizzle bypasses RLS**: it connects as the table owner and there is no `FORCE ROW LEVEL
SECURITY`. Don't reintroduce runtime Drizzle queries without revisiting the isolation
story — they would silently sidestep every policy.

## Hand-written migrations

drizzle-kit describes neither functions nor the `storage` schema, so these two are
written by hand and carry their own warnings inline:

- `0004_product_photos_storage.sql` — the `product-photos` bucket. Public for reads (the
  menu is opened from a QR code on mobile data, and a public URL is CDN-cacheable where a
  signed URL costs a round trip and expires); writes are owner-only through a
  `<venue_id>/<random>.<ext>` path the policies join back to `venues.owner_id`.
- `0007_adjust_product_stock.sql` — `adjust_product_stock`. `security invoker` with
  `set search_path = ''`, so RLS still applies and every name inside is schema-qualified.
  `security definer` would let any signed-in account decrement another venue's stock.
  `execute` is revoked from `public` — Postgres grants it by default — then granted to
  `authenticated` alone.
- `0009_order_functions.sql` — the three functions of counter ordering.
  `place_order` and `get_order` are **`security definer`**, the opposite choice, and for the
  opposite reason: the caller is `anon` and has no rights on `orders`, so the function is
  the only door and validates everything that comes through it. `accept_order` is
  `security invoker` — the caller is the manager, and RLS is exactly what must check the
  order is theirs. `execute` is revoked from `public` on all three, then granted to
  `anon, authenticated` for the first two and `authenticated` for the third.
  `src/features/orders/CLAUDE.md` holds the security reasoning; read it before touching
  `place_order`.

**Parameter names in these functions avoid every column name** (`guest_name` not
`customer_name`, `lookup_id` not `order_id`). Not style: in plpgsql, a parameter that is a
homonym of a column visible in the statement raises an ambiguity **at run time**, which is
the latest possible moment to find out.

## Connection strings

Three, from the Supabase dashboard: transaction pooler (6543, IPv4) for the app, session
pooler (5432, IPv4) for migrations if the transaction pooler chokes on DDL (set
`MIGRATION_DATABASE_URL`, read only by `drizzle.config.ts`), and the direct connection
(`db.<ref>.supabase.co:5432`), which is **IPv6-only** on recent projects and fails from
hosts without IPv6.

## Deliberately absent

i18n columns and per-venue theming, until their roadmap item comes up. No table numbers:
`orders.customer_name` is the reference, called out at the counter. No retention policy on
`orders` — it grows, and a purge belongs with a decision nobody has made.
`products.image_path` holds a Storage path, not a URL. `venues.owner_id` has no FK to
`auth.users` — `drizzle-orm/supabase` exports an `authUsers` reference that would make one
possible if that is ever wanted.

## Known weak point

`src/lib/supabase.ts` holds a **hand-written** `Database` type in snake_case: PostgREST
column names differ from Drizzle's camelCase, so the inferred types can't be reused.
Replace it with `supabase gen types typescript` once the Supabase CLI is wired up.
